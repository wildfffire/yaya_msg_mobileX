# 房间页拆分方案（`FollowedRoomsScreen`）

> **给谁看**：不写代码也能看懂路线与风险；动手的人按「每一节都给了完成标准」执行。
> **配套**：进度与验证记录写在 `docs/修复记录汇总.md`；排期地位见 `docs/优化方案_小白版_2026-09-28.md`。

---

## 0. 一句话

房间页现在的样子是：**一个 5323 行的文件里，最核心的那个组件就占了 3540 行，里面有 39 个状态、33 个回调。**
本方案的做法不是「一次大手术」，而是 **6 小步、每步都可单独回退**：
**先把纯计算逻辑搬出去并补上测试（前 4 步，零行为风险），有了安全网之后，才开始碰界面（第 5 步）和内部结构（第 6 步）。**

## 2. 为什么要拆 / 为什么难

**收益（按重要性排序）**

1. **改起来快**：想改「聊天气泡长什么样」，现在要在 3540 行里翻；拆完只在几十行里改。
2. **不容易改坏**：66% 的逻辑集中在一个组件里，改 A 常连带影响 B（本项目已经出现过「大小房间切换让消息区闪转圈」这类连带 bug）。
3. **能测**：纯函数能进 `npm run test:core`；组件内部逻辑现在**完全测不了**。
4. **滚动更顺**（间接）：抽成独立组件 + 防重复渲染之后，房间页（使用时长最高的页面）重渲染范围会明显变小。

**难点（必须正视）**

- **没有 React 测试环境**：项目刻意不装 jest / react-test-renderer（零测试依赖是它的既有风格）。
  这意味着**抽组件时无法自动证明「渲染结果与原来一致」** —— 所以顺序必须是「先补纯函数测试 → 再碰界面」，
  且碰界面那一步必须配一份**人工核对清单 + 真机回归**。
- **状态太多且互相牵连**：39 个状态里有相当一部分是「同一件事的多个镜像」（如消息、未读基线、定位标记）。
  抽取时一旦顺序错了，就会出现「闭包拿到过期值」这类难查问题。
- **它是直播链路的一环**：见 `优化方案` 第九节 —— 任何改动都要**全场景同步检查**（主直播页 / B站页 / 房间内直播与回放 / 播放器 / 小窗 / 弹幕链路）。

---

## 3. 总原则（5 条铁律）

1. **一次只搬一类东西**：一步只做「纯函数搬家」或「抽一个组件」，绝不混合。
2. **搬家 ≠ 改行为**：逐字搬运，连 `\uXXXX` 转义和中文标签都不顺手改（否则就没法证明等价）。
3. **每步独立可回退**：每步都只动 1~2 个文件 + 1 个新文件，回退就是删掉新文件、还原 import。
4. **先测后动**：搬走一类逻辑，就立刻给它补上单元测试；测试没到位不进入下一步。
5. **不碰业务规则**：不合并状态、不调整请求时机、不改文案 —— 那些是「优化」，不是「拆分」。

## 6. 明确不做（避免越做越乱）

| 不做 | 理由 |
|---|---|
| 顺手「合并那 39 个状态」 | 那是**业务重构**，不是拆分。先拆分再谈合并 —— 顺序反了会同时引入两类 bug。 |
| 顺手改样式 / 统一颜色 / 改文案 | 本项目有大量硬编码颜色（约 380 处）与未走 i18n 的中文标签；掺进拆分里就没法证明「只是搬家」。 |
| 一次性把文件砍到 1000 行 | 第 5、6 步天然要分多次做，每做一次都要真机回归，急不得。 |
| 为了拆分引入测试框架（jest 等） | 与项目「零测试依赖」的既有风格冲突；本方案用「纯 Node + tsc 编译」的既有模式解决纯函数测试。 |
